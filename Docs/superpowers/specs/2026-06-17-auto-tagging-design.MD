# 标签体系与 AI 自动打标设计

## 背景

当前项目已经具备以下基础能力：

- 视频解析任务与历史记录
- 提示词模板管理
- 标签组与组内标签管理
- 视频理解模型接入

但“正式标签体系 + AI 自动打标”尚未真正落地。当前系统更接近“把用户选中的标签文字拼进解析 prompt”，而不是完整的标签闭环：

- 没有独立的自动打标任务
- 没有结构化标签结果落库
- 没有视频主标签层
- 没有人工修订版本历史
- 模板解析与打标也尚未解耦

本设计用于补齐一期可上线的自动打标体系。

## 已确认需求

- 自动打标属于正式标签系统，不是只在报告里展示
- 自动打标与基于模板的解析必须分开
- 总体策略采用“混合模式”
  - 第一次读视频专门做自动打标
  - 模板解析默认复用自动打标的结构化结果
  - 只有高精度模板才再次读取视频
- 标签来源采用“固定标签库 + 自由标签”
- 标签结果采用“两层存储”
  - 分析记录保留原始打标结果
  - 视频主记录保存当前生效主标签
- 生效策略采用“AI 先生效，允许人工后改，并保留版本历史”
- 一期暂不做：
  - 复杂标签关系
  - 冲突规则引擎
  - 统计看板

## 目标

- 建立独立的自动打标任务链路
- 为视频生成可复用的结构化标签结果
- 将当前生效标签沉淀到视频主标签层
- 支持人工修订，并保留版本与变更历史
- 让模板解析默认复用自动打标中间结果，避免重复读视频

## 非目标

- 不在一期实现标签冲突自动裁决
- 不在一期实现标签统计看板
- 不在一期实现复杂层级规则与权重引擎
- 不在一期实现批量打标调度系统
- 不把自动打标强行塞进现有 `video_analyses` 表

## 方案对比

### 方案 A：单次读视频，双输出

做法：

- 一个模型请求同时输出自动标签与模板解析结果

优点：

- 调用次数少
- 表面上实现快

缺点：

- 自动打标与模板解析强耦合
- 模板变更无法独立重跑
- 结构化标签和长文本报告会互相影响稳定性
- 错误定位和测试复杂

结论：

- 不采用

### 方案 B：总是二次读视频

做法：

- 自动打标读一次视频
- 模板解析再独立读一次视频

优点：

- 两条链路彻底独立
- 模板解析精度更容易拉满

缺点：

- 成本高
- 时延大
- 同一视频重复消耗模型能力

结论：

- 不作为默认方案

### 方案 C：混合模式

做法：

- 自动打标独立读视频，产出结构化结果
- 模板解析默认复用结构化结果
- 仅高精度模板再次读视频

优点：

- 自动打标与模板解析解耦
- 成本与效果平衡
- 后续扩展空间最好
- 最符合当前一期目标

缺点：

- 需要补一套中间结果模型与状态管理

结论：

- 采用该方案

## 与现有实现的关系

### 继续复用的现有能力

- `tag_groups` / `tag_group_tags`
  - 继续承担“固定标签库分组”角色
- `prompt_templates`
  - 继续承担模板解析配置
- `video_analyses`
  - 继续承担模板解析任务与报告产物
- `tags`
  - 作为正式标签主表的复用基础

### 不建议复用为同一任务表的部分

- `video_analyses`
  - 不再同时承担自动打标任务
  - 自动打标需要结构化字段、命中项、版本演进，和报告型任务不是同一类数据
- `video_tags`
  - 当前老模型绑定的是 `videos.id`
  - 但现有视频解析主链路绑定的是 `uploaded_files.id`
  - 一期不直接复用该表作为当前主标签层，避免把新功能继续绑到旧视频域模型

## 总体架构

系统拆成两条相互协作但职责独立的链路：

### 1. 自动打标链路

输入：

- 视频
- 固定标签库
- 自动打标配置

输出：

- 结构化摘要
- 固定标签命中
- 自由标签候选
- 置信度
- 证据片段
- 原始模型输出

落库目标：

- 自动打标任务表
- 自动打标命中明细表
- 正式标签表
- 视频当前有效标签表
- 修订版本表

### 2. 模板解析链路

默认输入：

- 视频基础信息
- 当前有效标签
- 最近一次自动打标摘要
- 模板
- 用户自定义补充 prompt

可选增强：

- 当模板配置为高精度模式时，再次读取视频

输出：

- 现有 Markdown/文本分析结果
- 现有解析历史

## 数据设计

### 设计原则

- AI 原始结果与人工修订结果分层存储
- 当前有效标签与历史修订分开
- 优先复用已有 `tags`
- 自由标签允许进入正式标签表，但需保留来源
- 当前视频主标签层对齐 `uploaded_files`

### 一期表设计

#### 1. `video_auto_tag_tasks`

用途：

- 记录一次自动打标任务

核心字段建议：

- `id`
- `user_id`
- `video_file_id`
- `ai_config_id`
- `status`
- `progress`
- `prompt_version`
- `request_payload_summary`
- `raw_response`
- `structured_summary`
- `result_metadata`
- `processing_time`
- `token_usage`
- `cost_estimate`
- `error_message`
- `started_at`
- `completed_at`
- `is_active`

说明：

- `raw_response` 保存原始 AI 响应文本或裁剪后的 JSON
- `structured_summary` 保存模板解析可复用的结构化摘要
- `request_payload_summary` 只保存摘要，不保存超大 Base64 等敏感内容

#### 2. `video_auto_tag_items`

用途：

- 保存一次自动打标任务中的每个标签命中

核心字段建议：

- `id`
- `task_id`
- `tag_id`
- `tag_name`
- `tag_group_id`
- `tag_source`
- `match_type`
- `confidence`
- `evidence_text`
- `evidence_start_seconds`
- `evidence_end_seconds`
- `reason`
- `is_promoted`
- `is_active`

字段约束：

- `tag_source`：
  - `library`
  - `free`
- `match_type`：
  - `ai_detected`
  - `manual_added`
  - `manual_removed`

说明：

- 固定标签命中时，优先指向已有 `tag_id`
- 自由标签在入库前若无法映射到已有正式标签，可先只保留 `tag_name`

#### 3. 正式标签表 `tags`

用途：

- 保存系统正式标签定义

现状：

- 已存在 `tags`

建议增强字段：

- `source_type`
  - `library`
  - `free_promoted`
- `tag_group_id`
  - 可空，用于记录该标签来自哪个固定标签组
- `is_active`
  - 便于停用

说明：

- 一期不重做独立标签库表，优先增强现有 `tags`
- 固定标签可从 `tag_group_tags` 映射或同步生成到 `tags`
- 自由标签在满足阈值或人工确认后可进入 `tags`

#### 4. 视频有效标签表 `uploaded_file_tags`

用途：

- 保存视频当前生效标签

核心字段建议：

- `id`
- `video_file_id`
- `tag_id`
- `tag_name_snapshot`
- `source`
- `confidence`
- `auto_tag_task_id`
- `revision_id`
- `is_effective`
- `evidence_start_seconds`
- `evidence_end_seconds`
- `reason`
- `created_by`

字段说明：

- `source`
  - `ai_auto`
  - `manual`
  - `manual_override`
- `auto_tag_task_id`
  - 追溯来源任务
- `revision_id`
  - 追溯最近一次修订版本
- `is_effective`
  - 标识当前是否仍有效
- `evidence_start_seconds`
- `evidence_end_seconds`
- `reason`

说明：

- `uploaded_file_tags` 承担“视频当前有效标签层”
- 对外筛选、展示、模板复用优先读取这里
- 一期不直接复用老的 `video_tags`
- 老的 `video_tags` 后续如仍有业务使用，可在后续阶段评估迁移或并表

#### 5. `uploaded_file_tag_revisions`

用途：

- 保存一次人工修订的版本头信息

核心字段建议：

- `id`
- `video_file_id`
- `base_task_id`
- `revision_number`
- `change_reason`
- `created_by`
- `created_at`

说明：

- 每次人工修订创建一个新版本
- 不覆盖自动打标原始任务

#### 6. `uploaded_file_tag_revision_items`

用途：

- 保存某次修订中的标签变更明细

核心字段建议：

- `id`
- `revision_id`
- `tag_id`
- `tag_name`
- `action`
- `confidence`
- `note`

字段约束：

- `action`：
  - `add`
  - `remove`
  - `adjust`

## 标签来源策略

### 固定标签库

- 来源于 `tag_groups` / `tag_group_tags`
- 作为自动打标时的优先候选集合
- 推荐由系统在任务开始前统一整理为模型可消费的标签词典

### 自由标签

- 由模型在固定标签无法覆盖时补充
- 一期先允许生成，但不默认全部进入正式标签表
- 进入正式标签表的条件建议：
  - 置信度达到阈值，且
  - 未与现有标签重复，或
  - 经人工确认

## 自动打标流程

### 标准流程

1. 用户选择视频并触发自动打标
2. 后端读取固定标签库
3. 组装自动打标专用 prompt
4. 调用视频模型读取视频
5. 要求模型输出结构化 JSON：
   - 结构化摘要
   - 固定标签命中
   - 自由标签候选
   - 每个标签的理由、证据时间段、置信度
6. 后端校验输出并落库到 `video_auto_tag_tasks` / `video_auto_tag_items`
7. 将命中的正式标签同步到 `tags` / `uploaded_file_tags`
8. 自动打标任务状态更新为完成

### 同步到视频主标签层的规则

一期建议采用简单规则：

- 固定标签：
  - 直接进入 `uploaded_file_tags`
- 自由标签：
  - 默认仅保留在自动打标结果中
  - 达到阈值时可直接入 `uploaded_file_tags`
  - 人工确认后可进入 `tags` 与 `uploaded_file_tags`

建议初始阈值：

- `confidence >= 0.80`

说明：

- 阈值写入配置即可，不在一期做复杂规则引擎

## 人工修订流程

### 设计原则

- AI 自动打标结果先直接生效
- 人工修订后更新当前有效标签
- 原始 AI 结果不可被覆盖

### 标准流程

1. 用户查看视频当前有效标签
2. 用户手动新增、删除、调整标签
3. 后端创建新的 `uploaded_file_tag_revisions`
4. 后端写入 `uploaded_file_tag_revision_items`
5. 后端更新 `uploaded_file_tags` 当前有效状态
6. 保留原自动打标任务与命中项不变

### 人工操作范围

一期建议支持：

- 新增标签
- 删除标签
- 将自由标签提升为正式标签
- 给标签补备注
- 标记某个 AI 标签为误判

一期暂不支持：

- 批量合并标签
- 标签拆分
- 自动冲突裁决

## 模板解析复用策略

### 默认模式

模板解析默认复用以下中间结果：

- 视频当前有效标签
- 最近一次自动打标的结构化摘要
- 最近一次自动打标中的关键证据片段

默认不重复读视频。

### 高精度模式

当模板被标记为高精度模式时：

- 模板解析允许再次读取视频
- 同时仍可带上已有标签与摘要作为辅助上下文

### 推荐做法

- 普通模板：
  - 只复用标签和摘要
- 镜头级、脚本级、节奏级模板：
  - 二次读视频

## Prompt 设计

### 自动打标 Prompt 约束

自动打标请求必须要求模型输出稳定 JSON，不允许自由散文格式。

建议结构：

- `summary`
- `library_tags`
- `free_tags`
- `reason`
- `confidence`
- `evidence`

### 后端输出校验

后端必须做：

- JSON 解析校验
- 空字段兜底
- 置信度范围校验
- 证据时间段合法性校验
- 超长文本裁剪

## 错误处理

### 自动打标任务

- 模型调用失败：
  - 任务置为 `failed`
  - 保存错误信息
- 模型输出非 JSON：
  - 任务置为 `failed`
  - 保存原始响应摘要
- 标签映射失败：
  - 不中断整个任务
  - 将该项保留为自由标签候选

### 同步主标签层

- 正式标签写入失败：
  - 整个标签同步事务回滚
- 自动打标任务结果已保存，但主标签同步失败：
  - 明确记录为“结果已生成，同步失败”
  - 允许后续重试同步

### 人工修订

- 每次修订必须走事务
- 任一标签变更失败，整次修订回滚

## 事务与一致性

### 原则

- 自动打标任务结果写入与主标签同步分两个阶段
- 主标签同步与修订写入必须使用事务

### 推荐事务边界

- 阶段一：
  - 写入 `video_auto_tag_tasks`
  - 写入 `video_auto_tag_items`
- 阶段二：
  - 同步 `tags`
  - 同步 `uploaded_file_tags`
  - 记录同步状态
- 阶段三：
  - 人工修订写入 `uploaded_file_tag_revisions`
  - 写入 `uploaded_file_tag_revision_items`
  - 更新 `uploaded_file_tags`

## 风险与处理

- 风险：现有 `tag_group_tags` 与 `tags` 语义重叠
  - 处理：一期明确分工
  - `tag_group_tags` 负责固定标签库分组
  - `tags` 负责正式标签主表
- 风险：旧 `video_tags` 与当前 `uploaded_files` 主链路不一致
  - 处理：一期新建 `uploaded_file_tags`，不继续把新能力绑到旧 `videos` 域模型
- 风险：自由标签泛滥
  - 处理：先保留在任务结果中，满足阈值或人工确认后再提升
- 风险：模型 JSON 不稳定
  - 处理：强约束输出格式 + 后端严格校验
- 风险：人工修订覆盖 AI 原始结果
  - 处理：采用版本化设计，禁止覆盖原始任务结果
- 风险：模板解析误用旧标签
  - 处理：默认使用“最近一次成功且有效”的自动打标任务结果

## 验收标准

- 可以独立启动自动打标任务
- 自动打标结果能以结构化方式保存
- 视频能查看当前有效标签
- AI 自动打标可直接生效
- 人工修订后会生成新版本，不覆盖原始 AI 结果
- 模板解析默认复用标签与结构化摘要
- 高精度模板可以配置为二次读视频
- 相关前后端测试补齐并通过
